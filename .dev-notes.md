## Known issues / watch-outs

### JSON parsing from Sonnet
- Sonnet wraps JSON in ```json fences — always use _strip_fences() before json.loads()
- planning.py and profiling.py both fixed. Any NEW LLM call parsing JSON must do the same.

### ChromaDB
- Data is NOT in git — at backend/data/chroma_db/
- New machine: `cd backend && python setup_data.py`
- Per-job company doc collections (job_XXXXXXXX) are created at runtime and deleted on TTL
- No content validation on ingestion — a corrupted/binary source file will be silently chunked and
  served as real regulatory content with no error anywhere. Found one live instance of this
  (gdpr_recitals.txt, Session 29) that had apparently been in the knowledge base for months. Postgres
  rejects invalid UTF-8/NUL bytes on write, which is how it surfaced — Chroma has no equivalent check.
  If a source file looks suspiciously short/garbled after ingestion, check it directly with `file` and
  a NUL-byte scan before assuming the content is fine.

## Database migrations (Alembic)

Alembic is now set up at `backend/alembic/`. Use it for all schema changes going forward.

**New database setup (fresh Supabase project):**
```bash
cd backend
alembic upgrade head          # creates all tables
```

**Existing database (already set up with init_db):**
```bash
cd backend
alembic stamp head            # tells Alembic current DB is at 0001 without running migrations
```

**Add a new migration after changing models.py:**
```bash
cd backend
alembic revision --autogenerate -m "describe change"
alembic upgrade head
```

**Never change existing migration files** — always add new ones.

## Backups
No automated backups exist yet. Run manually before risky operations (migrations, re-ingests):
```bash
cd backend
python scripts/backup_db.py        # pg_dump of Supabase Postgres -> data/backups/db_<ts>.dump
python scripts/backup_chroma.py    # tar.gz of data/chroma_db -> data/backups/chroma_<ts>.tar.gz
```

off-host storage (S3/Backblaze) — local-disk-only backups don't survive a host failure.
